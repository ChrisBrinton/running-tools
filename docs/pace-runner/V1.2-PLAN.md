# PaceRunner V1.2 — Feature Plan

Captured from voice memos recorded mid-run, then grounded against the code.
Status is as of build 49.

**Read this as intent, not as a description of shipped behavior.** Line
references were verified when written; re-check before relying on them.

---

## 1. Dynamic cadence detection (the big feature)

Drive the tempo beat from the runner's **actual footfalls** instead of an
open-loop guess.

### What it does today

BPM is computed, never measured. `AppSettings.calculateBaseBPM`
(`AppSettings.swift:379`) is pure arithmetic:

```
steps per mile = 63360 / stride length in inches
BPM           = steps per mile / pace in minutes
```

plus a manual `cadenceOffset` (−15…+15 BPM, `RunConfiguration.swift:41`) and an
optional per-segment `strideLengthInches` override (`RunSegment.swift`). So the
beat is only as accurate as the configured stride length, it does not adapt as
form or fatigue changes stride within a run, and nothing aligns the beat's
*phase* with where the foot actually lands — the runner has to chase the click.

**There is no CoreMotion usage anywhere in the app.** This is greenfield.

### What V1.2 should do

- Read the accelerometer (CoreMotion) and detect footstrikes.
- Derive measured cadence (steps/min) and footstrike *phase* from that.
- Sync the beat to real footfalls rather than emitting a blind metronome, so
  the beat lands with the foot instead of near it.
- Use measured cadence — not assumed stride — to relate cadence to pace, and
  to drive pace-change guidance.

Open question from the memo, **not yet decided**: is this a one-time
**calibration** step (measure stride/cadence relationship, then run open-loop
against calibrated numbers), or **always-on dynamic** tracking? Likely both:
calibrate to seed, track continuously to correct. Needs a decision before
implementation.

### UI feedback

Surface measured footfall cadence next to the calculated/target cadence so the
two can be compared — "bring the two together" was the phrasing. This is also
the diagnostic that shows whether detection is working on-device.

### 1a. One golden source of pace deviation *(requirement, part of this feature)*

**There must be a single computed pace-deviation signal that both the voice cues
and the metronome consume.** Today they are computed independently and can
disagree — the metronome pushes one way while the voice says another.

Verified divergence, all of it live in `WorkoutManager.handlePaceUpdate`:

| | Metronome direction | Voice cues |
|---|---|---|
| Pace window | `mediumPace` only | `cascadingVoiceAlert`: slow → medium → fast, first one out of tolerance wins (`WorkoutManager.swift:1406`) |
| Comparison | `mediumPace − targetPace` vs `effectivePaceTolerance` | per-window deviation, **plus** directional filters that suppress an alert when another window disagrees |
| Start gate | shortest window filled (`movingTimeSpan >= fastAverageSeconds`) | `!isInGracePeriod && mediumAverageFilled` (medium window, 240s default) |
| Segment gate | window refill after a large-delta transition (§2) | same refill after a large-delta transition, otherwise 30s flat |

Still three separate axes of disagreement — §2 aligned the segment gate, but
window choice, tolerance handling, and the run-start gate remain independent.
The two subsystems can legitimately reach opposite conclusions at the same
instant, and at run start their gates differ by roughly two minutes (shortest
window, 120s, versus `mediumAverageSeconds`, 240s).

The fix is **one** deviation computation — window choice, tolerance, direction,
and suppression decided once — which both consumers then render, one as beat
emphasis/volume and one as speech. Consolidating this also makes the cadence
work above tractable: measured cadence becomes another input to a single
signal, rather than a third opinion.

Deliberately **not** being fixed yet — captured here as part of the V1.2
cadence work.

## 2. Segment transition smoothing — **implemented (build 44)**

When the target pace changes a lot between segments (warm-up → tempo), the
transition now behaves like the start of a new run rather than blending the
previous segment's data forward.

The problem, measured: `PaceWindows` moving averages were never reset at a
transition. The metronome reads `mediumPace` (240s default), so for minutes
after a 10:00 warm-up → 7:00 tempo transition the pace driving guidance was
still contaminated. With 120s of tempo running behind it, the medium window
reports ≈8:14/mile — 74 seconds per mile slower than actual. Voice cues got a
flat 30s grace period for this; the metronome got none.

What was added, all in `WorkoutManager`:

- **Restart the pace windows** on a transition whose pace delta is at least
  `segmentResetPaceDeltaSeconds` (20 s/mile). Minor steps between similar
  segments do not blank the windows.
- **Deferred execution.** `paceCalculator.reset()` publishes a nil pace
  synchronously, which re-enters `handlePaceUpdate` — and that takes the same
  non-recursive `stateLock` already held during segment tracking. The reset is
  flagged inside the lock and performed after release, matching the existing
  `shouldAutoEnd` pattern.
- **Every window restarts, master included.** Clearing the sample history
  restarts the distance-based rolling mile as well as the time-based windows,
  and drops `movingTimeSpan` to 0 so the §3 neutral hold re-engages through the
  same mechanism.

  Build 47 briefly spared the master window, on the theory that blanking it was
  what made the rolling mile duplicate the mile split. That theory was wrong —
  the duplication was a display bug (`PaceWindows.splitPace` aliased `slowPace`,
  fixed in build 48) — and sparing it measured worse on the Sep 8 run: across a
  10:40 → 9:20 transition the rolling mile took a full mile (536 s) to flush the
  warm-up, reading 10:24 → 9:56 → 9:34 while fast and medium had already
  settled. Because `cascadingVoiceAlert` consults the master window first, that
  produced actively wrong cues — calling for "speed up" at 9:56 while the runner
  was at 8:22. Restored in build 49.

  The moving-time and distance offsets and last-accepted anchors are preserved
  across the restart, so pause accounting stays continuous and carried
  cumulative distance cannot read as a phantom fast pace.
- **Short-segment cap.** The hold is capped at `neutralHoldSegmentFraction`
  (0.5) of the segment's estimated duration (`segment.distance.meters ×
  pace.secondsPerMeter`). Without this an interval shorter than the 120s window
  would be neutral end to end, which would leave intervals with no guidance at
  all.
- **Voice and metronome aligned at transitions.** When the windows were cleared
  for a segment, voice waits for the same refill the metronome waits for
  instead of its flat 30s. Previously the two would start directing roughly 90
  seconds apart. This is a step toward §1a, not a replacement for it — the two
  deviation calculations are still separate.

Logged under the `segment` category (`Pace windows restarted for new segment`)
and the `metronome` category (`Neutral hold ended`, now carrying the computed
hold and segment label).

**Coverage limit — read before trusting this.** The `PaceCalculator` mechanism
is unit-tested (`SegmentTransitionSmoothingTests`): reset clears the windows,
the post-reset window reports the new segment's pace, carried cumulative
distance does not produce a phantom pace, and the hold re-engages. The
`WorkoutManager` **wiring** is not unit-tested — the threshold check, the
deferred reset, the short-segment cap, and the voice gate. `WorkoutManager` has
four injected dependencies and the repo has no mocks for them, so covering it
means building that harness first. Until then this path needs on-device
verification with a real multi-segment run.

## 3. Metronome demonstrates before it directs — **build 45**

Reported from a run: at the start of a run *and* at the start of a sharply
different segment, the metronome "fires with an opinion (speed up/slow down)".

The neutral hold (§4) was working — the directional path is gated behind it and
could not have fired. The culprit was `setEmphasisBeatMode(0)`: mode 0 is
"normal emphasis", which still plays the distinct `emphasisBeat` tone. Neutral
to the pace logic, an accent to the ear.

While the beat is demonstrating footfall rhythm rather than encouraging a pace
change, every beat now sounds identical. `AudioEngine.setEmphasisBeatsSuppressed`
makes emphasis slots use the regular tone; it is driven by the same
`shortestWindowFilled` gate as the direction logic, and set explicitly at
workout start and at a segment reset so the state is right before the first pace
update arrives.

One trap worth keeping in mind: suppression changes the *tone*, not the rhythm.
The accent slot still sounds. With `audioBeatsEnabled: false` and
`emphasisBeatEnabled: true` the accent is the ONLY audible beat, so silencing it
would have left the entire neutral hold silent.

The decision is a pure function (`AudioEngine.selectBeat`) so it can be
unit-tested away from the audio thread — see `EmphasisBeatSuppressionTests`.

## 4. Also shipped

Two more items from the memos, both in build 43.

- **Neutral metronome start.** The metronome no longer directs faster/slower
  from the first seconds of a run. Root cause: `calculateTimeBasedPace` returns
  a pace once a window has `minSamples` (3) samples, so `mediumPace` went
  non-nil within ~3 seconds and the deviation logic engaged off a handful of GPS
  points — a window having a pace is not the same as a window being full. Added
  `PaceCalculator.movingTimeSpan` (moving-time span of retained samples, so
  pauses and excised GPS glitches do not count) and gated the metronome's
  volume modulation and directional emphasis on
  `movingTimeSpan >= fastAverageSeconds` (the shortest window, 120s default).
  Before that, the beat plays at steady full volume with no direction. The hold
  is now also re-armed at large segment transitions (§2), and during it every
  beat sounds identical (§3).

- **"9 o'clock" callouts.** Spoken announcements interpolated
  `Pace.formatted` ("9:00"), which `AVSpeechSynthesizer` reads as a clock time.
  Added `Pace.spoken` ("9 minutes per mile", "8 minutes 42 seconds per mile")
  and switched all four spoken sites; `formatted` remains the display form.

- **Beats never returning after a voice memo.** `AudioEngine` had no
  interruption handling, so an interruption stopped `AVAudioEngine`
  permanently while `AVSpeechSynthesizer` re-activated its own session on the
  next `speak()` — which is exactly why voice cues came back and drums did not.
  Added observers for `interruptionNotification`,
  `AVAudioEngineConfigurationChange`, and `mediaServicesWereResetNotification`;
  recovery on a serial queue (watchOS session activation blocks up to 8s); a
  full graph rebuild when the sample rate changes; and a 2s watchdog, because
  watchOS does not reliably deliver interruption `.ended`.

  **Needs on-device verification** — audio interruption cannot be exercised in
  the simulator. Start a run, record a voice memo, confirm beats return. Debug
  log lines to look for: `AudioEngine: interruption began/ended`,
  `beats resumed at N BPM`, `AudioEngine.watchdog: …`.

## Sync on install / update — **build 45**

Reported: after updating, the watch had not synced run configs; a day later it
had.

Cause: the dirty-latch model. The phone suppresses a config push when its
fingerprint already matches what it believes the watch holds. An install or
update leaves the counterpart with no configs while that latch still looks
clean, so nothing is pushed until some unrelated edit dirties it.

`AppVersionTracker.consumeLaunchKind()` compares the running build against the
last one recorded and reports `freshInstall` / `updated`. On a new version:

- **Watch** asks the phone for everything (`requestAllData`). Requesting rather
  than pushing is deliberate — the phone's `.allDataRequested` handler guards
  against answering with an empty set.
- **Phone** pushes configs, but only when it actually has some.

That empty-set guard matters in both directions: `syncAllConfigurations` is a
full REPLACE on the watch, so an empty push would wipe configs created there.

Needs on-device verification — WatchConnectivity cannot be exercised in the
simulator.

## Testing notes

`PaceCalculatorTests/testTimeWindowPacesDivergeWithNoisyData` is a **known
pre-existing flake** — it drives `PaceCalculator` with `Double.random` GPS noise
and fails roughly 2 in 9 runs on an unmodified tree. Skip it for a clean signal:

```
-skip-testing:PaceRunnerTests/PaceCalculatorTests/testTimeWindowPacesDivergeWithNoisyData
```

Confirm any suspected regression against a `git stash` baseline before blaming
a change.
